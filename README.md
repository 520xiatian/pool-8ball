**打开网页就能玩：** https://pool-8ball.linyuanyuan365.workers.dev

## 操作

按住台面往**白球反方向**拖动 = 拉杆，松手出杆。拖得越远力度越大，
底部有力度条实时反馈。瞄准时会显示出球方向、白球停靠虚影、被撞球受力方向。

犯规后对手获得自由球，白球会有黄色光环提示 —— 直接拖动它摆位。

台面右上角两个按钮：

- **2D / 3D** —— 俯视与透视视角互切，0.55 秒平滑过渡（不是硬切换，中间
  每一帧都是合法画面）。两个视角**功能完全对等**，3D 下同样能瞄准出杆，
  力度按台面上的逻辑距离算，所以换视角不会改手感。偏好会被记住。
- **🔊 / 🔇** —— 音效开关。击球、球撞球、撞库、落袋四种声音，音量和音调
  跟着物理算出的撞击强度变化。

## 部署到你自己的账号

```powershell
cd cloudflare
npm install
npx wrangler login          # 浏览器授权，免费账号即可
npx wrangler deploy
```

一条命令就把**网页和后端一起**部署好，自带 HTTPS。输出的地址直接打开即可。

网页文件在 `cloudflare/public/`，由 Cloudflare 边缘节点直接返回，不消耗
Worker 请求额度；只有 `/api` 和 `/ws` 会进 Worker 逻辑。

### 免费额度

截至 2026 年 8 月（[官方定价页](https://developers.cloudflare.com/durable-objects/platform/pricing/)）：
Durable Objects 在 Workers Free 可用，但**只能用 SQLite 存储后端**（本项目正是这么配的），
每天 10 万次请求、13,000 GB-s 计算时长 [cite:f044b39c-1]。
台球是回合制，一局几十次请求，够几百人同时玩。

用了 WebSocket Hibernation API，玩家思考的那 30 秒里 DO 会休眠，不计费 [cite:f044b39c-1]。

### 绑定自己的域名（国内直连）

Cloudflare 控制台 → Workers & Pages → 你的 Worker → Settings → Domains & Routes
→ Add custom domain。域名需要先托管在 Cloudflare（改 NS）。

绑了自有域名就不受 `workers.dev` 的 DNS 干扰影响了。

## 微信小程序版

同一套逻辑也做了小程序版，在 `miniprogram/` 目录。
导入微信开发者工具即可，`project.config.json` 已配好。

**联机后端三选一**，改 `miniprogram/config.js` 顶部一行：

```js
BACKEND: 'ws',   // 'none' 纯单机 | 'cloud' 微信云开发 | 'ws' 自建服务端
```

当前已配置为 `ws` + 上面的 Cloudflare 地址，开发者工具里勾选
**详情 → 本地设置 → 不校验合法域名**就能联机调试。

### 三种后端怎么选

| 后端 | 开发调试 | 朋友真机玩 | 要备案域名吗 |
|---|---|---|---|
| Cloudflare（`ws`） | ✅ | ⚠️ 需备案域名 | 要 |
| 本地 Node（`ws`） | ✅ 最方便 | ❌ | 不用 |
| 微信云开发（`cloud`） | ✅ | ✅ | **不用** |

关键限制：**微信真机要求 request/socket 的域名在小程序后台配置为合法域名，
而这要求域名有 ICP 备案。** `workers.dev` 和未备案的自有域名都过不了。
开发者工具勾「不校验合法域名」可以绕过，但只对模拟器和真机调试有效。

所以想让朋友用微信扫码就玩，要么绑备案域名，要么用微信云开发。
**网页版不受这个限制** —— 这也是为什么推荐直接玩网页版。

### 本地服务器（小程序开发最快）

```powershell
node server/index.js
```

会打印本机局域网地址，填进 `config.js` 的 `SERVER_URL`。
零依赖，内存存房间，重启即清空。详见 `server/README.md`。

> 这是**开发用**服务器：没有 TLS、没有速率限制、监听 `0.0.0.0`。
> 只在可信网络用，别端口转发到公网。

### 微信云开发

1. 开发者工具点**云开发** → 开通，复制**环境 ID**填进 `config.js` 的 `CLOUD_ENV`，
   并把 `BACKEND` 改成 `'cloud'`
2. 云开发控制台 → 数据库 → 新建集合 **`pool_rooms`**
3. 该集合权限设为 **所有用户可读，仅创建者可写**
4. 右键 `cloudfunctions/poolRoom` → **上传并部署：云端安装依赖**

第 3 步两个方向都不能错：**必须可读**（两端靠 `watch()` 收推送），
**必须不可写**（否则任何人能直接改库宣布自己赢了）。

因为文档对所有登录用户可读，云函数**不存 openid 原文**，只存
`sha256(openid + salt)` 的短哈希。

## 联机是怎么做到「不作弊」又「不卡顿」的

这是整个项目最值得说的部分，所有端共享同一套机制。

### 只同步一杆的参数，不同步坐标

一杆走球平均 90 帧、最长 131 帧。传每帧 16 颗球的坐标是每杆 18.8 KB；
只传出杆参数 `{dx, dy, power}` 连协议开销一共 **148 字节**（实测）。差 130 倍。

做法是让物理引擎**完全确定性**：给定同样的起始球态和出杆参数，
任何设备上都算出逐位相同的结果。于是两端各自本地跑一遍物理，画面自然一致。

为此 `physics.js` 有两条硬约束：

1. 模拟循环里只用 `+ - * /` 和 `Math.sqrt` —— IEEE-754 下结果唯一。
   **不用** `sin/cos/atan2/pow/random`，因为不同 JS 引擎实现可能有 1 ulp 差异，
   几百帧累积下来球会跑到完全不同的地方。
2. 瞄准方向以**整数向量**传输（放大 10000 取整），绕过浮点序列化精度问题。

测试里专门有一项：浏览器算出的球态与 Node 算出的必须逐字节相同。

### 谁说了算：服务端

客户端只上传意图，服务端用权威球态重跑同一份 `rules.applyShot`。
即使有人改了本地代码宣布"我进了黑八"，服务端算出来不是那样就不算。

四层校验（都有对应测试）：

- **身份**：确认你在房间里、确认轮到你
- **重放**：`shotIndex` 乐观锁，双击或重发被 `STALE_SHOT` 挡住
- **并发**：guard 条件写回，同时写只有一个成功
- **参数**：`sanitizeShot` 把 NaN、Infinity、零向量、超范围值挡在物理引擎外

三套后端的并发控制机制不同，行为一致：

| 后端 | 并发保障 |
|---|---|
| Cloudflare | Durable Object 同实例请求**串行执行**，天然无竞态 |
| 云开发 | `where({'game.shotIndex': n}).update()` 数据库层乐观锁 |
| 本地服务器 | 单线程事件循环 + guard 检查 |

DO 这个模型最省心：一个房间一个实例，平台保证串行，不用自己手搓 CAS。

### 手感：本地先动，服务端后校正

等服务端返回再播动画的话每杆都要等一个网络往返。所以客户端是
**出杆瞬间本地就起动画**，同时把这一杆发给服务端；动画播完时用
返回的权威 state 对齐。两端物理确定性一致，"对齐"通常是无事发生。

服务端拒绝时（比如手速太快在换手瞬间出杆），客户端丢弃本地动画、
重新拉权威状态回滚。

弱网丢推送导致杆号跳跃时（`newIndex !== prevIndex + 1`），
客户端不硬着头皮重放（那会算出错误画面），而是直接快照到权威局面 ——
宁可少一段动画，也不能显示错的。

## 为什么逻辑代码有五份副本

`physics.js`、`rules.js` 等在小程序、三个后端、网页目录各有一份，
且**必须逐字节相同**。各端都不能 require 小程序目录，只能复制。

```powershell
node scripts/sync-logic.js   # 改完 miniprogram/logic/ 必跑
```

浏览器版会被包装成 IIFE（补上 `module`/`exports`/`require` 三个局部变量），
但**源码一行不动** —— 这样才能保证物理判定完全一致。
包装逻辑在 `sync-logic.js`，配套的 `require` 实现在 `public/js/module-shim.js`。

`test-logic.js` 会验证所有副本是否同步，跑测试就不会忘。

## 规则实现

采用简化但完整可玩的中式八球规则（避免歧义）：

- 开球后第一颗合法落袋的球决定归属（全色 1-7 / 花色 9-15）；
  开球杆本身不定归属，符合大众打法
- **犯规**：白球落袋、空杆、先碰对方球、碰球后既无落袋也无碰库、
  未清台就打进黑八、该打黑八却先碰别的球
- **犯规惩罚**：对手获得自由球，可拖动白球到任意合法位置
- 己方球清台后进入打黑八阶段，黑八入袋即胜；提前打进黑八或打黑八
  这杆同时犯规，判负
- 每回合限时 45 秒，超时由**等待方**发起换手，服务端复核时间戳，
  防止篡改本地时钟偷回合
- 中途退出判定为认输
- 「再来一局」需双方都点过才重开，票上记着针对哪一局投的，旧票不污染新局

自由球摆位有个容易忽略的坑：台面边缘离腰袋中心只有 13.4 逻辑单位，
小于腰袋判定半径 23，白球一放上去下一帧就被判落袋。
`findFreeSpot` 会同时避开其他球**和**所有袋口的吞噬范围。

## 人机 AI

`bot.js` 是**候选采样 + 真实物理试算打分**：48 个方向 × 5 档力度共 240 个候选，
每个都用 `physics.simulate` 真跑一遍，按「进己方球 +1000 / 黑八时机 ±5000 /
犯规 -900 / 帮对手清台 -350」打分选最优。

因为 `simulate` 是纯函数，直接拿它当搜索的评估器 ——
AI 看到的世界和玩家完全一样，不存在"AI 作弊"。

实测开局思考 151ms、中局 130ms。
难度通过给最优解叠加"手抖"实现：新手偏差大，高手几乎不抖。

力度候选必须覆盖整条力度带（当前是 `[120, 300, 550, 800, 1000]`）。
这一点在把 power→初速改成开平方后踩过坑：原来的 `[420, 620, 820]` 换算下来
全挤在 63%~91% 初速区间，BOT 只会大力砸球，进球率从 0.25 掉到 0.17。
改物理参数时记得跑 `scripts/calibrate.js` 复核这组采样。

## 手感是怎么调的

物理内核本身（碰撞、动量交换、分离）一直是对的，但"像不像台球"另有几处：

**摩擦分两段。** 真实台球击出后先是**滑动**（球面相对台布打滑，摩擦大），
摩擦力矩很快把它转起来，达到 v = ωR 后进入**纯滚动**，此后只剩滚动阻力
（小约一个数量级）。所以远球的手感是"窜出去 → 悠悠滚很久 → 收住"。
早先一路恒定减速度，掉速线性，钝而无余韵。

`A_SLIDE`/`A_ROLL`/`MAX_V` 三个数是**配套标定**的，改一个就得重算。
每颗球记一个"滚起来的速度门槛"（初速 × 5/7，刚体球的标准结论），
速度在门槛之上算滑动段，掉下来就换小阻力。碰撞和撞库都会重置这个门槛 ——
这也是**定杆**的由来：正面对心撞完白球几乎不动（实测跟进 0.03~0.15 个球径），
随后才被摩擦重新蹭成滚动往前跟一点。

**力度→初速取平方根。** 滑行距离正比于 v²，直接线性映射的话"拖到 30%"
只能走 9% 的距离，前半段推不动、后半段骤然暴力。开根之后拖动距离和实际
走位近似成正比，中段走位力度才有分辨率。最低有效力度也从 60 降到 25。

**库边弹性 0.92 → 0.72。** 真实库皮约 0.6~0.75。0.92 下 5 库后还剩 66%
速度，球在库间弹个没完，像弹珠机。

**袋口缺口与判定半径严格互补。** 旧版缺口固定 `MOUTH = 30`，比腰袋判定半径
23 还宽，中间那 7 个单位是条死带：贴库走的球从那里出去，库边已经撤了、袋又
抓不住，于是飞出台面再被 `nearestPocket()` 兜底强判进袋 —— 画面上能看见球
穿出台边然后凭空消失。现在每个袋的缺口半宽算成 `sqrt(r² - R²)`，几何上保证
"进得去缺口的球一定被抓住，抓不住的一定撞库"。标定脚本里有一项就是拿 12 万
个球位验证再没有球跑出台面。

**声音由物理产生，不是渲染端猜的。** `simulate` 返回一条 `audio` 轨
（`[帧号, 类型, 响度]` 三元组），撞击强度直接来自法向相对速度。一帧内同类
只留最响的那声 —— 真实听感也是被最响的一下盖住，也挡住了开球瞬间几十条
几乎同时的事件把音频轨塞爆。网页端用 WebAudio 现场合成（带通噪声脉冲 +
指数衰减，不加载任何音频文件），小程序端播 `gen-sfx.js` 合成的 5KB WAV，
靠 `playbackRate` 区分三种音色。

**播放脱离刷新率。** 帧序列是按 1/60 生成的，早先按 rAF tick 逐帧消费，
144Hz 屏上整杆快 2.4 倍。现在按 `performance.now()` 累加真实时间取帧、
帧间线性插值 —— 高刷屏真的更顺滑，而不是更快。

**球面纹理跟着滚。** 号码和腰带沿运动方向扫过球面、转到背面时淡出，高光
固定在光源方向不动。这不是严格的球面贴图投影（25 像素的球上纯属浪费），
但三样一起动足够让大脑读成"在滚"而不是"两个圆片在平移"。

## 2D ⇄ 3D 视角

`renderer.js` 里只有一台相机，视角由 `tilt ∈ [0,1]` 连续控制：

- `tilt = 0` —— 俯角 90°、透视强度 0，等价于正交俯视（与旧版 2D 画面逐像素相同）
- `tilt = 1` —— 俯角 48°、视距 1250，透视：库边有厚度、近大远小

中间每个值都是合法画面，所以"切视角"是相机在连续移动，不是两套渲染器互换。
透视强度按 1/D 插值而不是插 D —— 直接插视距的话前 90% 行程画面几乎不动，
最后一瞬间猛地拉进来。

投影是 `project(x, y, z)`：台面 x 轴横向不变，y 轴按 sinφ 压缩，z 轴（离台布
的高度）在屏幕上是 `-z·cosφ`。俯视时 cosφ = 0，高度对画面毫无影响；越倾斜
库边和球的厚度才逐渐立起来。球心离台布 R 高，所以 3D 下球体比它的落点更靠上，
这个位移加上单独画的压扁椭圆阴影，就是"球坐在台面上"而不是"贴在台面上"。

反投影 `toLogic` 有解析解，不用迭代：因为透视缩放只依赖 y，可以先从屏幕 y
单独解出 y，再回代求 x。这是 3D 下能准确瞄准的关键，`test-render.js` 里拿
5 档视角 × 25 个台面点验证往返误差 < 1e-6。

几个实现上的坑：

- **只画朝向相机的立面。** 相机在台面中轴线正上方，所以左右两侧 x = 常数的
  立面是正侧向对着相机的，几何上完全看不见；画了反而在台布左右边缘留下两道
  贴边的亮线。
- **球要按纵深排序**（远的先画），否则近球会被远球盖住。
- **辅助线贴台布画**（z = 0），不能按球心高度画，否则线会浮在球上方，
  看着永远对不准。
- **`fit()` 用两遍法求缩放**：投影对 scale 是线性齐次的，先用 scale = 1 投出
  包围盒，再按画布尺寸整体放大。直接解析求解很麻烦（scale 影响透视、
  透视又影响包围盒）。

`renderer.js` 可以放心用 sin/cos —— 它只画画，不参与任何判定，各端浮点差异
最多让高光偏半个像素。`physics.js` 那边的确定性禁令不适用于此。

## 小程序上线须知

1. **小游戏类目需要资质。** 微信对游戏类小程序有额外类目审核要求，
   国内主体通常需要游戏版号。**个人开发者一般无法过审游戏类目。**
   建议先去微信公众平台确认帐号主体能选哪些类目。
2. **本地开发和体验版不受类目限制**，但体验版走真机，
   仍受 https + 备案域名限制（云开发除外）。
3. **网页版完全不受这些限制** —— 部署完就能分享给任何人。

## 后续可以加的东西

- **战绩与排行榜**：Cloudflare 加一个 Leaderboard DO；云开发建 `pool_players` 集合
- **观战**：`publicView` 已支持 `seat === -1` 的观战者视图，前端加只读模式即可
- **旋转球（塞）**：目前只模拟了"滑动→滚动"这一层，没有上下塞和侧旋 ——
  玩家无法选择击球点，也就没有拉杆、跟杆、走位塞这些手法。要做得给球加角速度
  字段并参与碰撞与库边反弹，等于重写 `physics.simulate`：注意别引入不确定的
  三角函数运算，否则破坏跨端确定性，而且服务端那三份副本要一起改。
- **袋口几何**：现在球心进入判定圆就瞬间消失，没有袋角碰撞、没有在袋口转两圈
  掉进去、没有打铁弹出。加袋角圆弧碰撞体能明显提升"进球那一下"的观感。
- **PWA**：加个 manifest.json 和 service worker 就能"添加到主屏幕"离线玩单机
- **对手掉线提示**：服务端加心跳字段，前端已有重连骨架
